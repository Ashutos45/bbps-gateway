1 Introduction
This API document provides the integration framework for Bank of Baroda as a BBPOU on the Bharat 
Bill Payment System (BBPS) through the Customer Onboarding Unit (COU). It includes API 
specifications, request/response formats, authentication methods, and compliance requirements to 
facilitate a secure and efficient PayBill, Fetch Bill, and Generate Biller List File API process.

2 Headers and Authentication
 The details of Headers and Authentication process is given below:
2.1 Request Header Attributes
With each request, you will need to set request headers as below:
 Content-Type
Request Content-Type to take the values application/json
 Accept
Accept Response Content-Type to take the values application/json
 BD-Traceid
Traceid is used for idempotency and the request with the same Traceid within the day will be rejected. 
Traceid can be alphanumeric without any spaces or special characters and should be a maximum size of 
30.
 BD-Timestamp
Transaction timestamp in the yyyymmddhh24miss format
 Authorization
This will be generated by the client as explained in the steps below and validated by BillDesk prior to 
processing the request. Format of the header is HMACSignature clientid:hmacvalue
2.2 HMAC Request Signature
The process to generate the Authorization Request Signature is as below:
Step 1:
Receive a clientid and a secretkey from BillDesk. The clientid identifies the client sending the requests, and 
the secretkey is used to generate the hash for the request.clientid = client1 and secretkey = 
3FF9CBF87A66A452
Step 2:
Create the data string that is input to generate the HMAC-SHA256 hash.
hmac_string = HTTP-Method + "|" + URI + "|" + Content-Type +"|"+ Accept + "|"+ BD-Traceid + "|" + BD-
Timestamp + "|" + SHA256(Requestbody)
HTTP-Method = POST (Upper case)

You can initiate a payment request in any of the following three ways. Payment based on a validated 
request, using a validationid and, billid when available. Payment against a presented bill, using a bill ID. An 
adhoc payment, using the billeraccountid or the authenticators and billerid (without a validationid or billid). 
The response will contain the payment object for valid payment requests.
 The payment workflow will need to be preconfigured for a source. The following workflow can be 
supported based on the value of the parameter authorization_type in the request:
 In case the payment is already authorized (debit completed by source), the parameter 
authorization_type is not required in the request. The request will create a successful payment 
resource in the BillPay system. The payment_status in the response is returned as “PAID”.
Schedule: This value can be passed for the request parameter to schedule an auto payment for a future 
date. The payment will be processed as per the regular workflow of auto-payment
Authorize: This value can be passed for the request parameter to create a payment resource where debit is 
initiated by BillDesk. The response can have payment_status as “PAID”, “FAILED”, or “DELIVERED” based on 
the status of the debit process.
Onhold: The source can define a payment workflow to be completed in a two-step process, in which case 
this value can be passed to create a temporary payment resource. The payment_status in the response is to 
be returned as “PENDING”. The source can then perform any other authentication, process the debit, and 
call the “Approve Payment” API to complete the payment process.
